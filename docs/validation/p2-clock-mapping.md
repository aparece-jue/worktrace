# P2 开工前：单调 / 墙钟映射实测记录

06 §4 把「单调/墙钟映射」列为**实现前**技术验证，结论会反过来决定 P2 的异常阈值与
状态机（总纲 §5 第 9 条）。本文是该实验的记录，探针在
`src-tauri/examples/clock_probe.rs`。

**探针不改系统时间。** 锁屏、休眠、正反改时全部由人工操作；操作前按一次回车打标记，
汇总里就能把人为干预与自然漂移分开。

## 2. 判定口径（08 §1，P2 Task 2）

- 阈值 `THRESHOLD_MS = 2000`，**严格大于**才越界；恰好 2000ms 不算。
- **两个差都要看**，任一越界即进入异常判断：
  - **相邻增量差** `d_wall - d_mono`：这一拍两个时钟走得是否一样快；
  - **累计偏差** `(wall - wall₀) - (mono - mono₀)`：从起点算总共差了多少。
- 只看相邻增量会漏掉**缓慢累计漂移**（每次几十毫秒、单次永不越界，但累计会越界）。
  这一条由单元测试 `slow_cumulative_drift_is_caught_even_though_each_step_is_small` 钉住。
- 单调钟**倒退**是硬故障（正常平台永不出现）；挂钟倒退是正常的用户行为。

## 3. 自然漂移基线（无人工干预）

命令：`cargo run --example clock_probe -- --seconds 60 --interval-ms 1000`

| 指标 | 值 |
| --- | --- |
| 采样数 | 60（1 秒间隔，共 60 秒） |
| 采样失败 | 0 |
| 越界（>2000ms） | 0 |
| 相邻增量差最大值 | **1 ms** |
| 累计偏差最大值 | **14 ms** |
| 挂钟倒退次数 | 0 |
| 单调钟倒退次数 | 0 |
| 间隔偏离最大值 | 1 ms |
| 疑似挂起次数 | 0 |

明细片段（每行 `idx,wall_ms,monotonic_ms,d_wall,d_mono,delta_gap,cum_gap,flag`）：

```text
56,1791009059287,56021,1001,1000,1,13,
57,1791009060287,57021,1000,1000,0,13,
58,1791009061288,58022,1001,1001,0,13,
59,1791009062289,59022,1001,1000,1,14,
60,1791009063289,60022,1000,1000,0,14,
```

### ⚠ 这台机器上发现的关键数字：累计偏差按 ~10–14ms/分钟增长

相邻增量差始终是 0 或 ±1ms（两个时钟**每一拍都同步**），但**累计偏差**单向增长。
三次独立时长的实测：

| 时长 | 采样数 | 累计偏差 | 相邻增量差最大 | 折算速率 |
| --- | --- | --- | --- | --- |
| 60 s | 60 | 14 ms | 1 ms | **14.0** ms/min |
| 300 s | 300 | 70 ms | 1 ms | **14.0** ms/min |
| 600 s | 600 | 100 ms | 1 ms | **10.0** ms/min |

**速率不是常数**：前两次完全一致，第三次降到 10 ms/min。这说明两个时钟之间不是
一个恒定的走时差——系统时间在被 Windows 时间服务逐步校准（slew），所以累计偏差
会增长、也会被部分拉回。**所以判据不能依赖具体数字，只能依赖「周期性重建锚点」
这个机制本身。** 照此区间外推：

```text
2000 ms ÷ (14 ms / 60 s) ≈ 8570 s ≈ 2.4 小时   <- 按前两次实测
2000 ms ÷ (10 ms / 60 s) ≈ 12000 s ≈ 3.3 小时  <- 按第三次实测
```

**含义**：如果 P2 的累计偏差检查是「相对本次 run 的锚点、绝对值 > 2000ms 即判异常」，
那么**在没有任何用户干预、没有休眠的正常会话里，两三个小时后它会自己触发**——
把一个完全健康的会话判成异常并推入 recovering。

**这正 06 §4 要「实现前」做这个实验的原因**（总纲 §5 第 9 条：「结论可能反过来改设计」）。

### 成因已查明：**不是取整误差，是真实走时差**

一开始怀疑这是 Windows 计时器量化（默认 15.6ms）造成的取整偏差单向累积。
**已用实测排除**——探针在启动时以最快速度连读两万个样本，测出各自的实际分辨率：

```text
wall_systemtime:   samples=20000  min_positive_ns=100  max_ns=4200  zero_permille=642
                   distinct_deltas=[0, 100, 200, 300, 800, 900]
monotonic_instant: samples=20000  min_positive_ns=100  max_ns=8400  zero_permille=663
                   distinct_deltas=[0, 100, 200, 300, 800, 900]
```

**两个时钟的分辨率都是 100ns**（Windows 的 FILETIME / QPC 粒度），不存在「一个粗一个细」
的情形。所以那 14ms/分钟**不是读取粒度造成的假漂移**，而是：

> **系统时间（被 Windows 时间服务向 NTP 校准）与 QPC（跟着硬件走、不受校准）之间
> 约 233 ppm 的真实走时差。**

这比原先的猜测**更严重**：它不是实现问题，是**这两个时钟本来就必然会分叉**。

两个后果：

1. **「相对 run 锚点的绝对累计偏差 > 2000ms」这个判据在原理上就是错的**——它检测的不是
   异常，而是时间流逝本身。
2. 按 10～14 ms/min 外推，**任何超过两三小时的正常会话都会被误判为异常**；
   而且这个数字随 NTP 校准状况浮动，不能当作硬边界。

### 由此得出的结论（不再是不确定项）

**锚点必须周期性重建，累计偏差只能相对「最近一次重建」来衡量。**

心跳本来每 30 秒一次，是天然的重新基准点。按 14ms/min 折算：

```text
30 秒窗口内的累计偏差 ≈ 14 ms/min × 0.5 min = 7 ms
```

远低于 2000ms 阈值。所以「每次成功心跳前移锚点」既能滤掉时间流逝本身，又能保住
对真实异常的灵敏度（真实异常是**单拍**跳几千毫秒，不是每分钟十几毫秒）。

**替代方案**（速率判据：累计偏差 ÷ 已运行时长 > 某 ppm）也能解决，但比前移锚点复杂，
且要另定 ppm 阈值——**倾向前移锚点**。

**据此对 P2 的待定问题**（写进第 7 节）：

- 累计偏差应该**相对什么**比？相对 run 锚点会随时间线性发散；相对「上一次被接受的
  样本」则只反映单拍行为，等于退化成相邻增量差。
- 是否该改成**速率**判据（例如累计偏差 / 已运行时长 > 某 ppm）而不是绝对毫秒数。
- 是否该在**每次成功心跳**时把锚点前移（心跳本来每 30 秒一次，是天然的重新基准点）。
- 阈值 2000ms 对「相邻增量差」显然够宽（实测 ±1ms）；对「累计偏差」则要重新论证。

结论：

- 单调钟全程未倒退。
- 相邻增量差与累计偏差都远低于 2000ms 阈值；在这台机器上，**没有人为干预时不会
  触发异常判定**，阈值不会被自然漂移误伤。
- 累计偏差的增长速率是本实验最值得记的数：它决定「长时间运行后累计偏差会先于
  相邻增量差越界」需要多久。

## 5. 阈值结论

- 2000ms 是否合适：**待人工操作段填完后定**。
- 已知：自然漂移在 60 秒内累计不超过个位数毫秒，离阈值极远。
- 若 4.3（调快时间）产生的跳跃远大于 2000ms（预期如此），说明阈值能可靠区分
  「用户改时」与「自然漂移」。

## 6. 未验证项（**不要当成已验证**）

- 探针是**前台进程**，它证明不了「关窗后仍在采样」——那需要 P7 建立的周期采样驱动。
- 它也证明不了**系统事件（锁屏/休眠通知）的可靠性**与到达延迟；那属于 P7 的正式
  事件接线，由 P7 实测、P6 硬化、P8 最终验收。
- 本题结论只覆盖**这台机器 + 这个 Windows 版本**。换机器或换系统要重跑。
- `FakeClock` 的单元测试通过**不代表**实机行为已确认；两者分别登记状态。

## 7. 对 P2 的影响（做完后回填）

      心跳前移锚点**，30 秒窗口内的漂移约 7ms，远低于阈值。
