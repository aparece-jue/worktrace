# Worktrace V0.1 实施计划总纲

> 本文件是**计划序列的索引与边界契约**，不是可执行计划。每一份具体计划单独成文，落在同一目录下。
> 写代码前必须先确认本文件：它决定后面每一份计划的接口基线。

**目标版本：** V0.1 —— `捕获 → 计时 → 修正/恢复 → Today → 最小导出/周回顾 → 备份`（05 §1）
**验收全集：** F-001…F-011、F-014…F-020（共 18 项，见 04）
**上游规格：** `docs/superpowers/specs/2026-10-02-worktrace-architecture/` 的 00–08 与 99

## 1. 为什么要切成 8 份

本计划采用的拆分原则是：**一份计划只覆盖一个能独立交付、可独立测试的子系统**。整套设计横跨 M00–M13、V0.1–V1.0，塞进一份计划会得到一份谁也无法评审、执行者也无法一次读进上下文的文档。

切分依据是 01 §2 已经写死的核心实现链：

> 核心实现链：M02 → M01 → M04/M05 → M06 最小统计 → M07 最小导出与回顾；M12 外壳可以使用 mock 提前搭建，随后逐条接入。M00 的单实例在持久化初始化前生效；托盘与服务接线由 M11 完成。

切分判据（每一条都必须成立，否则不拆）：

1. **可独立测试**：这份计划跑完，能用 `cargo test` 或可复现的手工步骤证明它对了，不需要等后面的计划。
2. **接口可登记**：它产出的函数签名 / DTO / 命令契约，后面的计划以实现验收后的签名为基线引用；调整时同步消费者。
3. **审查可分离**：一个评审者可以否掉这一份而批准相邻那份。

顺序不是任意的：**P2 必须先于 P3**（会话命令全部走同一个协调器，先把协调器做出来，命令才有地方落），**P5 必须在 P3/P4 之后**（统计读的是它们写的事实），**P8 最后**（完成统计/恢复/导出与发布验收）。

P4 与 P2 无依赖，可在 P1 后并行；P3 依赖 P4 日期/时区能力，必须在 P4 后实施。

### 计划的编写节奏：总纲先行，详细计划逐份迭代

**契约级计划可提前编写；每份执行前根据已验收代码复核真实签名、技术选型和依赖。** 采用以下编写约束：

> **No Placeholders** —— 计划里不得引用"在任何任务中都未定义的"类型、函数或方法。

P5 消费 P3/P4 的契约，P7 先消费 P1/P2/P4 服务，P8 再接入 P3/P5/P6。提前定义任务、输入输出和验收；实现级签名在前置代码验收后登记，不把猜测签名当作已经存在的代码。

正确的分工：

| 层 | 何时定 | 内容 | 现实偏离时怎么办 |
| --- | --- | --- | --- |
| **本总纲** | 现在 | 范围、依赖顺序、产出接口的**名字**、F-ID 覆盖、横切约定 | 更新总纲；这是路线图，本来就会修订 |
| **详细计划** | 契约提前写，执行前复核 | 任务拆分、接口/事务契约、可执行验证步骤 | 前一份的**真实签名**已经存在，直接引用 |

于是实际推进是：

1. **现在**：总纲及八份详细计划已编写；P1 已实现并验收，P2–P8 尚未实施。
2. **P2 与 P4 计划已编写，实施未开始**（P4 与 P2 无依赖，故与 P2 一并写出）。
3. **八份计划已全部编写完毕**（P1–P8，契约级）。剩下的不确定性包括**真实 Rust 签名、执行边界与依赖选型、平台实验结果**——各计划都写了「在 P1 真实接口基础上定稿并登记」，即实现时按实登记、必要时回头同步总纲与消费者。
4. **实施顺序**：**P1 → P2 → P4（P2 与 P4 无依赖，可并行）→ P7 → P3 → P5 → P6 → P8**。
   **P7（外壳）为什么排第 4 而不是最后**：06 §4 把「双窗口同步」列为**实现前**技术验证，它需要两个窗口才能跑；01 §2 也明写「M12 外壳可以使用 mock 提前搭建，随后逐条接入」。把外壳压到最后会让这条实验无处可做，平台风险（IPC、状态镜像、托盘、窗口生命周期）也要等到收尾才暴露。P7 因此只做**不依赖 P3/P5/P6** 的部分（捕获→理清→计时、状态镜像、托盘、窗口），「统计/恢复/导出」的界面留在 P8。

**总纲里"产出接口"那一列因此不是装饰**：它是相邻两份计划之间唯一的契约面。写 P2 时引用的是 P1 那一列；写 P3 时可能发现 P2 实现时改了签名——那就**先更新总纲**，再写 P3。

## 3. 逐份计划的边界

每份计划的详细任务在各自文件里。这里只锁**边界与接口**——这是防止后一份计划推翻前一份的关键。

### P1 · 领域模型与持久化基座

- **文件**：`2026-10-03-worktrace-v01-foundation.md`
- **做**：V0.1 的 12 张表与索引、`user_version` 迁移、`data_epoch`/`revision` 信封、Task 状态机（02 §5 全表）、Session/Interval 状态机与四条不变量、Task 与 Session/Interval 仓储（含 `task_change` 审计）、可伪造的双时钟接缝
- **产出接口**（后续计划直接引用，修改时同步总纲与消费者）：`storage::db::Db`、`storage::migrations::{migrate, SCHEMA_VERSION}`、`storage::meta::{Meta, read_meta, init_meta, bump_revision}`、`error::AppError`、`commands::envelope::WriteEnvelope`、`storage::guards::{guard_epoch, guard_row_version}`、`domain::task::{TaskStatus, TransitionCause}`、`domain::session::{SessionState, SessionMode, TimerKind, SessionTransition}`、`domain::interval::{IntervalFacts, IntervalRange}`、`storage::task_repo::*`、`storage::session_repo::*`、`storage::checkpoint_repo::*`（接受调用方事务及已验证时间事实）、`platform::clock::{Clock, ClockSample, SystemClock, FakeClock}`、`platform::paths::db_path`
- **不做**：无 IPC 命令、无恢复审计业务服务；提供 interval_checkpoint 事务写入原语、`goal`/`milestone` 不建表
- **覆盖**：F-001…F-005、F-008、F-014、F-015、F-017、F-019 的**存储与领域部分**

### P2 · 计时协调器与检查点

- **文件**：`2026-10-03-p2-timer-coordinator.md`
- **做**：08 §1 与 §7 的全部计时语义——归属基线 `anchor_wall_at`/`anchor_monotonic` 与 `A(M)`；约 30 秒心跳同事务写 `interval_checkpoint`；关闭时用单调差得 `duration_ms` 并令统计 `ended_at = started_at + duration_ms`；**两项阈值检查**（相邻增量差与相对基线的累计偏差，各自 > 2000ms 触发异常）；阈值内小幅校时不改基线；新 run / 休眠后 / 显式校正后重建基线；tick 与查询 DTO（`data_epoch`、`revision`、`run_id`、`session_id`、`session_version`、`tick_seq`、`as_of`、`active_ms`、`state`、`timer_kind`、`remaining_ms`/`overtime_ms`）由**同一协调器快照**产出
- **产出接口**：`services::timer::Coordinator`（串行、单实例），`start/pause/resume/finish` 的**业务层**原语，tick 采样函数
- **不做**：崩溃扫描与 `reconcile`（P3）；暂停/恢复/结束的 IPC 命令（P7 接线）；番茄钟阶段（V0.2）
- **覆盖**：F-006、F-007 的核心

### P3 · 恢复确认、历史修正与补录 ✅

- **文件**：`2026-10-03-p3-recovery-and-history.md`
- **做**：02 §3 命令表里**四个事后命令**的实现——`reconcile`（仅 recovering）、`correct`（仅 finished）、`backfill`（手工补录）、`discard_session`（作废整次）。**`start/pause/resume/finish` 归 P2**，本计划只消费它们的已提交事实，不重复实现；`switch` 属 V0.2。02 §4 的四类判定扫描（可信 paused 保持、running 有开放区间 → recovering 且只标该区间、recovering 保持、不变量损坏隔离）；消费 P2 已提交的可信前缀/待确认余段；启动扫描使用共享恢复原语，不另实现实时异常分割；确认/历史修正的区间裁剪与分割（半开区间、跨日按时区日界）；`time_edit` 审计；`correct` 仅 finished、`reconcile` 仅 recovering
- **产出接口**：各命令及 transition_task 的 `Result<Dto, AppError>`；恢复扫描入口（启动时调用）
- **不做**：统计口径（P5）；UI（P7）
- **覆盖**：F-003 任务状态联动、F-006、F-008、F-009（核心侧）、F-015、F-017

## 5. 横切约定（每份计划都继承）

1. **分层与依赖方向**（01 §2 + 仓库 `AGENTS.md`）：`commands/ → services/`；services 可依赖 storage/domain/platform，storage 只依赖 domain 和共享类型，domain 不依赖 platform，`events/` 横切。`domain/` 禁止 IO；`storage/` 禁止调用 `platform/`；`commands/` 禁止直连 SQL。每份计划的验收都跑那两条 grep 自查。
2. **工具链固定**：`cargo` 命令一律在 `src-tauri/` 下运行。仓库在 Windows 盘，Windows 与 WSL 两套工具链都是 1.98.1；**同一次执行只用一套**，交替使用会让 `target/` 反复全量重编。`rusqlite` 用 `bundled`，不依赖系统 SQLite。
3. **错误契约**（00 §4）：预期失败一律 `Result<T, AppError>`，必带 `code`/`message`/脱敏 `detail`。`code` 是前端唯一的分支依据。禁止对可预期错误 `unwrap()`。
4. **写事务信封**（00 §5）：修改命令带 `expected_data_epoch` 与 `expected_row_version`；一次业务写让 `revision` **恰好 +1**；心跳、tick、纯读不加。任何被拒的用户命令**自身不改 revision、不写审计、不留半条记录**；时钟异常产生的独立系统状态事务按第 9 节另计——这条在 P1 计划中要求测试，后续计划沿用同一断言风格。
5. **测试策略**：不变量与跃迁用 Rust 测试钉死；时间一律经 `platform::clock::Clock` 注入，测试用 `FakeClock`；库用 `Db::open_in_memory()` 或 `tempfile` 临时文件。**不要求一仓储函数一个机械测试**（01 §3）。
6. **人工验收单列**：涉及 UI、托盘、窗口、OS 事件（F-009、F-011、F-016、F-020 及 F-007 的事件注入）的部分，计划里必须给出**可复现的手工步骤**，不能用单元测试冒充实机验证（08 §6 的要求）。
7. **改动纪律**：只碰计划列出的文件。既有前端文件与 `greet` 命令保留不动，直到 P7 明确处理。
8. **断言口径**（计划正文只写"测什么用例"，"断言什么"按本条统一）：
   - **被拒的用户命令**在没有独立系统状态事务时必须断言四件事，缺一不可：① `revision` 与调用前相等；② 目标表的行数不变（新建被拒时该新实体不存在）；③ 审计表（`task_change`/`time_edit`）没有新增行；④ 本操作涉及的已有记录与关联区间字段值和调用前一致，尤其状态、版本、归属、起止、时长、待确认及作废标记。若独立异常事务已提交，则以该事务提交后的事实为用户命令比较基线，并单独断言系统事务的合法变更（见第 9 节）。只断言"返回 Err"是无效测试——错误可能在写完一半之后才返回。
   - **幂等操作**（重复打标、重复加入今日计划、重复归档）必须断言第二次调用后 `revision` 不变，且返回值明确表示"集合没有变化"。
   - **CHECK 约束**必须断言**具体那条** INSERT/UPDATE 被拒，并覆盖边界值（等于阈值不算越界：`2000ms` 不触发、`2001ms` 触发；`ended_at = started_at` 的 0 长度区间合法）。
   - **错误码**必须断言 `code()` 的字符串，不是断言"是个错误"。`DATA_EPOCH_MISMATCH` / `VERSION_CONFLICT` 同时要断言 `message()` **不含** epoch 字面量与 SQL 片段。
   - **time 相关**一律用 `FakeClock` 显式推进，禁止在测试里读真实时钟。
   - **仓储函数不接受隐式时间**：测试要能证明"改系统时间不影响已算出的 `duration_ms`"，做法是只推进 `FakeClock` 的挂钟而保持单调钟不动。

9. **规格里的权威清单必须逐条核对，不能只靠各自的测试列表。** 这三处是规格明写的清单，每份计划在完成门槛处对照与自身相关的条目逐条确认，并在人工验收记录里写明"已核对/不适用"：
   - **02 §8 M01/M05 必测案例**（14 条：暂停后重启、暂停直接结束、恢复前台冲突、并发 start、跨午夜含暂停、空范围、同名根标签、历史工时重叠、强杀后十秒内重启、运行/暂停时退出、前后改系统时间、旧版本编辑冲突、区间修正后报表重算、待确认排除与显式确认）；
   - **04 §9 必做集成用例**（迁移失败、磁盘不足、重复提交、旧版本修改、跨午夜暂停、统计修正）；
   - **06 §4 实现前技术验证**（DB 执行边界、单调/墙钟映射、双窗口同步、HUD/构建）——前两项在本轮范围，结论可能反过来改设计，**必须在对应计划开工前完成并记录**。
   这些清单的条目在计划里大多已被各自的测试列表覆盖，但没有核对点就没人能确认"14 条都过了"。

## 9. 本轮评审后的执行基线

（下面第 1 组是跨计划的接口与事务基线；「异常事务、用户命令拒绝与查询的边界」是其中的时序规则。）

P1/P2/P4 已改为任务与接口契约，不保留未经编译的完整实现代码。复选框表示实施状态，当前均未开始。P1 实现验收后，按真实签名复核 P2/P4；接口允许审核后调整，但必须同步总纲与消费者。

- 业务服务拥有事务；仓储写入函数接受调用方事务，不自行提交、不自行加 revision。单次业务服务统一加一次 revision，检查点写入不加。
- P2 负责所有实时异常分割及 recovering 跃迁；P3 消费 recovering 事实并处理启动扫描、确认和历史修正，不重复分割。
- P2/P4 可用测试驱动服务验证；单实例和正式进程启动接线由 P6/P7 完成。正式初始化顺序始终是单实例检查 → 库打开/迁移 → 创建 run/扫描 → 协调器 → 窗口。
- 共享错误位于 src-tauri/src/error.rs；storage 不反向引用 commands。commands 不接受 Connection，事务内 epoch/version 校验由 storage::guards 提供。
- 全部业务操作，包括新建，带 expected_data_epoch；更新既有可编辑对象带其版本。关系增删用明确幂等集合操作，不以读到当前 epoch 再比较自身代替请求校验。
- 系统事件可信边界自动暂停；不可信/延迟事件进入 recovering，不能把所有事件一律作异常，也不能因心跳间隔跳过事件。

### 异常事务、用户命令拒绝与查询的边界

统一执行顺序：先验证请求 epoch、目标存在性和 expected_row_version；失败直接拒绝用户命令，不借该无效请求采样或写异常事实。通过后，协调器取得一次样本并检测。如果存在需改变事实的时钟异常，先作为独立系统状态事务完成分割、审计和 recovering 跃迁，revision 增加一次；随后原用户工作命令返回 RECOVERY_REQUIRED，不再执行用户意图，也不再增加 revision。拒绝响应携带异常事务提交后的权威 epoch/revision/session_version；前端刷新，不自动重试原命令。

系统事件及定时采样可独立发现并提交异常，不依赖有效用户请求；旧版本/旧 epoch 请求本身不能触发写入。查询在正常采样时是纯读、不增加 revision；检测触发的恢复事务属于系统状态变化，提交后再返回一致快照，不能宣称这次检测全过程没有写入。异常事务失败不提交部分事实，不应用内存状态；停止输出新的可信暂计并进入明确故障处理，不将可疑样本作为普通成功结果。

必测：旧 epoch/旧版本请求同时遇到异常时，命令拒绝不产生写入；后续独立采样能正常发现异常。有效 pause/resume/finish 检测异常时只提交一次系统恢复事务，原意图不执行；重复异常不重复分割/审计。正常查询 revision 不变，异常查询返回提交后的快照及 revision。字段级回滚断言分别以用户命令前或独立异常事务后为基线，不把合法系统变更误判为用户命令的部分提交。

### 新增计划的接口选择

P3 依赖 P4 的 LocalDate/时区能力；历史修正统一以 session.row_version 校验并增加版本，不新增区间版本列。P3 拥有任务状态编排服务；P7 预留入口，P3 完成后由 P8 接入并启用托盘完成等联动动作。P5 在同一串行边界内取得采样与一致读快照；作废记录不是待确认。P6 恢复维护态同时隔离周期采样和在途操作，成功/失败重开后均创建新运行态，不继承旧基线。

### 轻量 GTD 首版范围与提前外壳
