# Worktrace V0.1 实施计划总纲

> 本文件是**计划序列的索引与边界契约**，不是可执行计划。每一份具体计划单独成文，落在同一目录下。
> 写代码前必须先确认本文件：它决定后面每一份计划的接口基线。

**目标版本：** V0.1 —— `捕获 → 计时 → 修正/恢复 → Today → 最小导出/周回顾 → 备份`（05 §1）
**验收全集：** F-001…F-011、F-014…F-020（共 18 项，见 04）
**上游规格：** `docs/superpowers/specs/2026-10-02-worktrace-architecture/` 的 00–08 与 99

## 1. 为什么要切成 7 份

技能 `writing-plans` 的 Scope Check 要求：**一份计划只覆盖一个能独立交付、可独立测试的子系统**。整套设计横跨 M00–M13、V0.1–V1.0，塞进一份计划会得到一份谁也无法评审、执行者也无法一次读进上下文的文档。

切分依据是 01 §2 已经写死的核心实现链：

> 核心实现链：M02 → M01 → M04/M05 → M06 最小统计 → M07 最小导出与回顾；M12 外壳可以使用 mock 提前搭建，随后逐条接入。M00 的单实例在持久化初始化前生效；托盘与服务接线由 M11 完成。

切分判据（每一条都必须成立，否则不拆）：

1. **可独立测试**：这份计划跑完，能用 `cargo test` 或可复现的手工步骤证明它对了，不需要等后面的计划。
2. **接口可冻结**：它产出的函数签名 / DTO / 命令契约，后面的计划可以直接引用，不需要回头改。
3. **审查可分离**：一个评审者可以否掉这一份而批准相邻那份。

## 3. 逐份计划的边界

每份计划的详细任务在各自文件里。这里只锁**边界与接口**——这是防止后一份计划推翻前一份的关键。

### P1 · 领域模型与持久化基座 ✅

- **文件**：`2026-10-03-worktrace-v01-foundation.md`
- **做**：V0.1 的 12 张表与索引、`user_version` 迁移、`data_epoch`/`revision` 信封、Task 状态机（02 §5 全表）、Session/Interval 状态机与四条不变量、Task 与 Session/Interval 仓储（含 `task_change` 审计）、可伪造的双时钟接缝
- **产出接口**（后续计划直接引用，不得改名）：`storage::db::Db`、`storage::migrations::{migrate, SCHEMA_VERSION}`、`storage::meta::{Meta, read_meta, init_meta, bump_revision}`、`commands::envelope::{AppError, WriteEnvelope, guard_epoch, guard_row_version}`、`domain::task::{TaskStatus, TransitionCause}`、`domain::session::{SessionState, SessionMode, TimerKind, SessionTransition}`、`domain::interval::{IntervalFacts, IntervalRange}`、`storage::task_repo::*`、`storage::session_repo::*`、`platform::clock::{Clock, SystemClock, FakeClock}`、`platform::paths::db_path`
- **不做**：无 IPC 命令、无 `time_edit`/`interval_checkpoint` 写入函数、`goal`/`milestone` 不建表
- **覆盖**：F-001…F-005、F-008、F-014、F-015、F-017、F-019 的**存储与领域部分**

### P2 · 计时协调器与检查点

- **做**：08 §1 与 §7 的全部计时语义——归属基线 `anchor_wall_at`/`anchor_monotonic` 与 `A(M)`；约 30 秒心跳同事务写 `interval_checkpoint`；关闭时用单调差得 `duration_ms` 并令统计 `ended_at = started_at + duration_ms`；**两项阈值检查**（相邻增量差与相对基线的累计偏差，各自 > 2000ms 触发异常）；阈值内小幅校时不改基线；新 run / 休眠后 / 显式校正后重建基线；tick 与查询 DTO（`data_epoch`、`run_id`、`session_id`、`session_version`、`tick_seq`、`as_of`、`active_ms`、`remaining_ms`、`state`）由**同一协调器快照**产出
- **产出接口**：`services::timer::Coordinator`（串行、单实例），`start/pause/resume/finish` 的**业务层**原语，tick 采样函数
- **不做**：崩溃扫描与 `reconcile`（P3）；暂停/恢复/结束的 IPC 命令（P7 接线）；番茄钟阶段（V0.2）
- **覆盖**：F-006、F-007 的核心

### P3 · 会话命令、崩溃恢复与修正

- **做**：02 §3 命令表的业务实现（`start/pause/resume/finish/switch/discard_session/backfill/correct/reconcile`）；02 §4 的四类判定扫描（可信 paused 保持、running 有开放区间 → recovering 且只标该区间、recovering 保持、不变量损坏隔离）；异常时的可信前缀保留与余段 `needs_review`；区间裁剪与分割（半开区间、跨日按时区日界）；`time_edit` 审计；`correct` 仅 finished、`reconcile` 仅 recovering
- **产出接口**：各命令的 `Result<Dto, AppError>`；恢复扫描入口（启动时调用）
- **不做**：统计口径（P5）；UI（P7）
- **覆盖**：F-006、F-008、F-009（核心侧）、F-015、F-017

### P4 · 项目、标签与今日计划

- **做**：`project` 的建/重命名/归档与"归档项目不出现在新建任务选择列表"；`tag` 四类（Domain/Activity/Context/Report）与层级；`task_tag` 权重（同一 kind 非空权重 0..1、总和 >1 拒绝、<1 显示未分配、**不自动归一化**）；`daily_plan` 今日选择列表（按用户时区，不用 `updated_at` 推断）

## 5. 横切约定（每份计划都继承）

1. **分层与依赖方向**（01 §2 + 仓库 `AGENTS.md`）：`commands/ → services/ → storage/ → domain/ → platform/`，`events/` 横切。`domain/` 禁止 IO；`storage/` 禁止调用 `platform/`；`commands/` 禁止直连 SQL。每份计划的验收都跑那两条 grep 自查。
2. **工具链固定**：`cargo` 命令一律在 `src-tauri/` 下运行。仓库在 Windows 盘，Windows 与 WSL 两套工具链都是 1.98.1；**同一次执行只用一套**，交替使用会让 `target/` 反复全量重编。`rusqlite` 用 `bundled`，不依赖系统 SQLite。
3. **错误契约**（00 §4）：预期失败一律 `Result<T, AppError>`，必带 `code`/`message`/脱敏 `detail`。`code` 是前端唯一的分支依据。禁止对可预期错误 `unwrap()`。
4. **写事务信封**（00 §5）：修改命令带 `expected_data_epoch` 与 `expected_row_version`；一次业务写让 `revision` **恰好 +1**；心跳、tick、纯读不加。任何被拒的调用**不改 revision、不写审计、不留半条记录**——这条在 P1 已立测试，后续计划沿用同一断言风格。
5. **测试策略**：不变量与跃迁用 Rust 测试钉死；时间一律经 `platform::clock::Clock` 注入，测试用 `FakeClock`；库用 `Db::open_in_memory()` 或 `tempfile` 临时文件。**不要求一仓储函数一个机械测试**（01 §3）。
6. **人工验收单列**：涉及 UI、托盘、窗口、OS 事件（F-009、F-011、F-016、F-020 及 F-007 的事件注入）的部分，计划里必须给出**可复现的手工步骤**，不能用单元测试冒充实机验证（08 §6 的要求）。
7. **改动纪律**：只碰计划列出的文件。既有前端文件与 `greet` 命令保留不动，直到 P7 明确处理。

## 8. 待确认事项（写代码前需要定）

1. **计划文件放哪**：目前只存在会话工作区 `docs/superpowers/plans/`。规格在仓库的 `docs/superpowers/specs/` 下，同步脚本（`worktrace-sync-diagram.ps1`）只覆盖 specs 目录。要让计划跟仓库走（后续会话与子代理读得到），需要给脚本加 `docs/superpowers/plans/` 一段。
2. **`core.autocrlf`**：仓库未设该配置，22 个源码文件工作区是 CRLF、索引是 LF。P1 之后的每个提交都会碰 Rust 源码，行尾不统一会让 diff 失真。建议先 `git config core.autocrlf true` 再 `git add --renormalize .`。
3. **本总纲与 P1 是否评审通过**：P2–P7 的边界一旦据此写死，后续改动成本会上升。
