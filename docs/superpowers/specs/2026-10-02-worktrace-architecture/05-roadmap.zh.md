## 0. 先收敛设计，再逐条交付

本轮仅修订文档，没有实现 SQLite、计时或 HUD。先评估本方案，随后用小实验确认数据库阻塞边界和计时策略；HUD/多入口试验独立，不阻塞基本记录。无需先创建全部空目录、提交并推送才能开始功能；文档发布和代码提交另由用户工作安排决定。

MUI/emotion 依赖清理、Dockview 正式用途在评估后执行；不删除已复制组件。选择 Rust→TS 类型工具时验证维护状态与 Tauri 2 兼容性。

## 2. V0.1 纵向交付顺序

1. M02/M01：Project/Task/Tag 最小 CRUD、迁移、数据库约束、revision 与错误契约；M00 单实例必须在库初始化前接入。
2. M04/M05：启动、暂停、恢复、结束，持久化 work_interval；先测试暂停直接结束/重启、并发 start/resume、改时和区间重叠。
3. M12/M03：Inbox/Today/计时操作贯通；实现监听先于快照、响应版本过滤和轻量版本校验；M11 最小托盘调用同一服务。
4. M05/M06：恢复确认、人工补录/修正、跨范围裁剪、确认/运行暂计/待确认分列。
5. M07/M01：JSON 明细与 Markdown 简单周回顾、手动备份与完整恢复路径；演练失败恢复，不等 V1.0 才保护真实数据。
6. 所有 V0.1 条目通过后进行两周本人真实使用；记录漏记/忘停/修正频率、捕获/切换操作负担、周回顾是否实用。

实现每步都交付命令、持久化、UI、必要测试和演示；模块规格只写下一步需要的内容。预计工期在实验和真实闭环完成后评估，不凭模块数量估算。

## 3. 后续依赖与范围

- V0.1b：HUD 五项原生属性与 DPI/多屏、Locked/Edit、热键冲突处理；Mini 是否同时做待用户评估。失败的 HUD 原型可暂缓，但不能把退化方案算原验收通过。
- V0.2：M06/M07 扩展统计/报表，M05 并发/打断，time_block/Goal/Milestone/依赖/WBS；M08 只做估时误差与知识事实，不提前承诺熟练度评分。M13 只查已有实体，中文/型号检索有实测；SQL LIKE/FTS5 的选择不先锁死。
- V0.3：先 M09 所选输入组包、预览与发送确认，再 M10 建议和反馈历史。数据只取已有实体，analyze_context/review_week 高级接口按后续已有能力开放，不要求一次实现全部八接口。
- V0.4：简要 ContextFact/Decision、文件引用与结构化 Agent 导入；按 07 校验/去重/审阅后采纳。M13 只搜索应用记录与引用标题，不提取或索引源文件正文。
- V0.5：先使用事实与样本数，再可选实验能力模型；KPA/扩展回顾基于已确认数据，不以采纳率证明 AI 节省时间。
- V0.2（**回顾与互动图表**，用户 2026-10-12 提出，设计方针待重新评估后再定稿）：
  日/周/年回顾都要图，直方图 + 扇形/环形图，**可互动**（选中切片显示内容）、**可选信息维度**
  （日度既可列具体做的事，也可只按标签/类别看）。落地前先定五件事：
  1. **聚合放后端还是前端**：建议**后端**——不是性能问题，而是口径唯一（日界裁剪、时区、
     人工/机器/等待分列都已有经验收的实现，前端再算一遍必然分叉）；
  2. **维度模型**：任务 / 项目 / 标签 / 会话类型（人工·机器·等待）/ 一天中的时段 / 星期几 / 月，
     「换维度」而不是「换一张图」；
  3. **互动深度**：悬停显示数值是最低档；要支持**点选下钻**（选中标签 ⇒ 列出该标签下的具体区间与时刻）
     与**跨图联动**（选中切片后其余图只剩该子集）——对应后端需要"按维度聚合"与"按条件取明细"两类接口；
  4. **图表库选型**（项目当前只有 antd、**没有图表库**）：ECharts / Recharts / visx / Observable Plot 之间选，
     ⚠️ 新依赖会进打包产物，**必须过 `check-bundle.ps1` 门禁**并评估体积（当前安装包仅 2.9 MB）；
  5. **不变量不得破**：图里**绝不能出现"人工 + 机器"的合计**；跨午夜按后端给的 `range.to` 裁剪；
     时间一律用查询时区。
  💡 便宜路子：既有 JSON 导出已含 `confirmed / pending / totals` 与逐区间明细，
  图表可先直接吃它（"回顾图表 = 导出的可视化"），省一个后端接口——是否需要"任意维度实时切"再决定走哪条。
- V0.6：**自动升级**。落地前必须先定的六件事（这些是决策，不是实现细节）：
  1. **更新源与托管**：GitHub Releases / 自建静态站 / 内网镜像，决定可用性与是否要把发布流程搬上去；
  2. **签名密钥的所有权与保管**：Tauri updater 要求公钥内置、私钥离线保管——**私钥丢失等于所有已装版本再也无法自动升级**，
     必须在第一次发布更新前就把密钥备份与轮换方案写清楚；
  3. **检查时机与用户可见性**：启动静默检查 + **提示后由用户确认安装**（推荐）还是静默下载 + 重启安装；
     托盘/菜单里要有"检查更新"的手动入口，且**离线时不得打断使用**；
  4. **通道**：stable / beta 是否分叉，以及 beta 怎么退回 stable；
  5. **失败与回滚**：下载中断、签名不匹配、安装失败一律**保留旧版可运行**；升级后若数据被新版本写过，
     旧版本必须拒绝写入（沿用既有"未来版本拒写"规则），因此**升级前自动备份**应作为默认动作；
  6. **与现有安装方式的关系**：当前是 NSIS、`INSTALLMODE=currentUser`、装到 `%LOCALAPPDATA%\Worktrace`，
     数据在 `%APPDATA%\com.worktrace.desktop\`（升级必须原样保留）——就地升级要覆盖这条路径，portable/免安装形态需另行说明。
  7. **打包形态定为 NSIS，且把身份三要素冻结**（2026-10-12 决定）：`bundle.targets` 由 `"all"` 收成 `["nsis"]`
     （`all` 会同时产出 MSI 与 NSIS，两个安装形态并存正是"必须先卸载旧版"的典型来源）；
     `installMode` 显式写 `"currentUser"`（别靠默认值——一旦变 `perMachine`，安装目录与注册表 hive 都变，自动升级路径直接断）；
     **安装目录永不改、`identifier` 永不改、数据永不放进安装目录**（数据现在在 `%APPDATA%\com.worktrace.desktop\`，是对的）。
     做到这三条，更新永远不需要卸载；反之改动它们**必须走一次手动卸载/重装**。
  8. **已装版本不会自动升级**：当前 0.1.0 构建时未开 `createUpdaterArtifacts`，自身不含 updater ⇒
     **第一个带 updater 的版本需要手动重装一次**才进轨道。这是预期行为，不是缺陷，应写进验收判据。
  9. **两种签名别混**：updater 的 minisign 签名（免费，保护更新包不被篡改）**不等于** Windows 代码签名
     （决定是否弹 SmartScreen"未知发布者"，需付费证书）；两者密钥各自保管。
  ⚠️ 实测约束：本机出现过**受限网络下下载失败**（NSIS 工具首次下载报 socket 权限 10013、代理不可达），
  所以更新源的可达性、超时与"检查失败"的用户提示要按**可能长期不可用**来设计。
- V1.0：已有备份/迁移功能的自动化与硬化，故障注入和长期运行，不把数据保护留到此版首次实现。

## 4. 依赖、风险与决策门槛

核心链：M02 → M01 → M04/M05 → M06 最小集 → M07 最小集；M12 外壳可先 mock，之后逐段联通。搜索不依赖统计，HUD 不占核心链；M09 最小集必须早于 M10。

| 风险 | 交付前验证 |
| --- | --- |
| 数据库阻塞/锁竞争 | 计时、查询、备份并行负载及 busy/disk-full 失败路径 |
| 时间口径错误 | 暂停跨午夜、改时、强杀立即重启、运行暂计与恢复确认 |
| 窗口陈旧 | 快照竞态、末事件丢失、旧查询晚到、隐藏重开 |
| 数据丢失 | 一致备份、迁移失败、未来版本拒写、恢复失败保留原库 |
| 产品过重 | 两周真实使用后再决定 HUD/分屏/复杂分类是否值得增加 |

## 5. 实施规格约定

每个规格列：范围/F-ID、命令与 DTO、事务与不变量、错误/重试、测试、人工验收、与上游差异。实现状态单列“未开始/进行中/已验收”，不能用文档状态代替。必要测试以不变量为中心，不要求一仓储函数一个形式测试。

本轮实施检查补充：M01 先验证 epoch 切换与 ContextFact 取代事务；M04/M05 验证提交到内存基线的串行边界及旧 tick；M06 验证 recovering 中可信闭合工时仍计入。R-01～R-08 已批准，上述协议与恢复行为修订待审核。

当前产品边界（2026-10-03）：个人工作记录与任务管理，包含能力短板分析和 KPA 工作证据整理；文件读取、OCR、正文提取和正文搜索交给外部 Agent 与配套 skill。见 [范围与导入契约](07-scope-and-agent-import.zh.md)。

能力成长闭环：短板线索 → 用户确认 → 学习/练习任务 → 工作样本与自评 → 复盘；保留可选熟练度模型。KPA 收集可追溯成果与时间点，不自动评判人员绩效。

实施细节补充见 [08：计时、阶段、AI 与报告快照](08-implementation-contracts.zh.md)。

V0.1 的 M04/M05 先验证 08 的时间映射与检查点；V0.2 番茄钟阶段以休息不计工时为门槛；V0.3 纳入 F-209/F-210；V0.4 outcome 最小存储早于导入；V0.5 确认报告快照和能力行动复盘。

V0.2 pomodoro_cycle 与 work_interval.cycle_index 一起落地，先验统一 pause/resume 和本轮预算恢复，再接阶段 UI；不新增重复 IPC 工作命令。

## 6. 工作量基准（实测，2026-10-12）

口径：仓库 2026-10-02 首个提交 → 2026-10-12，**302 个提交**；只统计 tracked 的源码/脚本/文档
（排除 `node_modules` / `target` / `gen` / `dist` / 图标 / 锁文件）。

| 类别 | 行数 |
| --- | --- |
| **Rust 业务代码**（domain 1,167 / services 11,823 / storage 3,692 / platform 3,008 / commands 3,348） | **23,949** |
| **Rust 测试**（`src-tauri/tests/`） | **49,557** |
| **前端源码**（pages 8,534 / state 3,263 / types 1,677 / components 705；其中测试 9,114） | **16,505** |
| 契约快照 JSON（30 份） | 710 |
| 脚本（ps1/py） | 445 |
| 文档（`docs/*.md`） | 12,152 |
| 验收手册（`manual-*.md`） | 1,507 |
| **合计** | **≈ 104,800** |

三个结论，供后续估算复用：

1. **业务代码只占约 30%**（Rust 24k + 前端业务 ~7.4k ≈ **31k 行**）；其余是测试、文档、脚本与契约快照。
2. **测试是业务代码的 2.07 倍**（49.5k : 24k）——**工作量的大头在验证，不在功能**。
3. 框架脚手架（Tauri/Vite/AntD 模板、图标、锁文件、`gen/schemas`）总计仅数百行；
   `platform/` + `storage/` 那 6.7k 行是自研基础设施，不是模板。

**吞吐锚点**：P8 阶段 = 19 个提交 / 20,405 行净增，交付 13 条命令 + 8 块页面 + 产物门禁 +
托盘跳转 + 两份验收文档；V0.1 全程 10 天完成 20 个 F 项。

**后续版本预估**（±50%；V0.1 最贵的是地基——schema/迁移、revision+epoch 协议、错误契约、
计时协调器、崩溃恢复——后续版本直接复用，边际成本下降）：

| 版本 | 新增业务代码 | 含测试总量 | 日历时间 |
| --- | --- | --- | --- |
| V0.1b（HUD / 全局热键 / 模式） | 2.5–4k | 6–9k | 3–5 天 |
| V0.2（并发、打断、权重、排期、报表与回顾图表、实体搜索） | 8–12k | 25–35k | 2–3 周 |
| V0.3（AI 建议：组包/预览/发送确认 + 反馈历史） | 4–7k | 12–20k | 1.5–2.5 周 |
