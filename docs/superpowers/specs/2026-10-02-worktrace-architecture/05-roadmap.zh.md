## 2. V0.1 —— 底座

**目标**：一个能真正开始记录工作的最小闭环。做完就能用它记工时，哪怕功能很少。

### 需要的 spec / plan（按实现顺序）

| 顺序 | 模块 | spec 文件建议名 | 说明 |
| --- | --- | --- | --- |
| 1 | M00 平台层 | `M00-platform-spec` | **仅**单实例 + 托盘最小集；HUD 相关的窗口样式留到第 8 步 |
| 2 | M03 事件总线 | `M03-events-spec` | 事件类型表、信封、`revision` 持久化、`get_snapshot()` |
| 3 | M02 领域模型 | `M02-domain-spec` | 实体、Task 状态机、WorkSession 生命周期与不变量 |
| 4 | M01 存储层 | `M01-storage-spec` | 完整 DDL、迁移框架、仓储接口、备份 |
| 5 | M04 Timer Engine | `M04-timer-spec` | 时刻制时钟、`timer.tick`、休眠校正 |
| 6 | M05 WorkSession | `M05-session-spec` | 生命周期、不变量、崩溃恢复标记 |
| 7 | M12 前端骨架 | `M12-frontend-shell-spec` | 主题、布局、`domainState.ts`、Today + Inbox |
| 8 | M11 窗口系统 | `M11-windows-spec` | 托盘、Basic HUD（含 §4.5 的 Locked/Edit） |

### 可并行

- 第 7 步的**外壳部分**（主题 / 布局 / 路由）可在第 4 步完成前先用 mock 数据开工
- 第 1 步与第 2 步互不依赖，可并行

### 风险

| 风险 | 触发点 | 应对 |
| --- | --- | --- |
| Win32 鼠标穿透不达预期 | 第 8 步 | 已在第 0.3 步提前实测；若不可行，HUD 退化为"置顶 + 无焦点"（放弃穿透）并记 ADR |
| 同步 rusqlite 阻塞 IPC | 第 4 步 | 已在第 0.3 步实测线程模型；必要时统一 `spawn_blocking` |
| HUD 多入口构建不通 | 第 8 步 | 已在第 0.3 步实测；退路是单入口 + 路由参数（牺牲启动速度） |

### 必守边界
- AI 不得成为 Core 的硬依赖（SPEC §5.2）
- AI 建议不得覆盖 `source = user` 的字段（SPEC §5.3 / `F-205`）
- `STRICT_LOCAL` 数据不得进入任何外发路径（SPEC §31 / `F-208`）—— **这条需要可验证手段，不是口头承诺**

## 8. 关键路径与排期纪律

**严格串行的关键路径**：

```
M02 → M01 → M04 → M05 → M06 → M07
```

链上任一环滑期，下游全部顺延。排计划时优先保它，其余都可让路。

**可并行池**（不占关键路径）：
- M13 搜索（依赖 M01/M02）

## 9. spec / plan 的编写约定

每个模块的 spec 用统一骨架，便于交叉引用：

```markdown
# Mxx <模块名> 设计规格

| 项 | 值 |
| 状态 | 草案 / 已评审 |
| 上游 | 00-architecture / 01-module-breakdown |
| 覆盖条目 | F-xxx, F-yyy |
| 对应 ADR | ADR-xxx |

## 1. 职责与边界（含"不负责什么"）
## 2. 接口契约（命令 / 事件 / 数据结构）
## 3. 内部设计
## 4. 错误与降级
## 5. 测试策略（含必须覆盖的不变量）
## 6. 与上游文档的差异
```

**硬要求**：`## 5` 必须列出该模块要守的**不变量**与对应测试，否则 spec 不算完成。这是 ADR-002（分层靠纪律）能否撑住的唯一保障。
