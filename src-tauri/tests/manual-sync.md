# 双窗口同步实机实验（P7 Task 6a；6b 的「时序验证」共用）

> **为什么必须实机做**：这个实验要验的是**两个真实 WebView 之间的事件广播时序**——Tauri
> 把一条 `domain.changed` 投给两个窗口的先后、隐藏/最小化时那条通道与定时器的行为、以及
> 真实 IPC 下「旧响应晚到」长什么样。集成测试进程里**没有事件循环、也没有第二个 WebView**
> （`tauri::test` 的 mock 运行时本轮没有启用），所以 `cargo test` 钉不住这些现象。
>
> **自动化那半边已经做了什么**（`src/state/__tests__/dualContextSync.test.ts`，提交
> `b7b9250`，fix round 1 之后是 `684d495`）：两个**各自独立**的 `domainState` 上下文 +
> 一个共用的假后端（一个假事件总线），证明的是「**同一套规则在两个上下文里各自成立**」
> ——跨上下文失效与重新取数、旧响应被丢弃（按**本视图水位**，与页面同一份契约）、
> 末次事件丢失后 30 秒内收敛、跳号取新快照、重复通知不再失效。
> 它**证不了**真实双 WebView 的广播时序。**不要把那份单测当成实机结论**
> （总纲 §5 第 9 条：不得把仓储/服务层测试标为「UI 已验收」）。
>
> 每一步记**观察到的现象**（数字、时刻、截图路径、SQL 结果），不要只写「通过」。
> 外壳侧的其他人工验收（托盘、关窗后继续计时、单实例唤起）在
> [`manual-shell.md`](manual-shell.md)，两份文档互相引用。

### 本轮 debug 命令观测日志（2026-10-05）

`commands::dev::CommandProbe` 由真实 `run_command` 包装消费，debug 控制台输出 `[worktrace] probe:` JSON：`id/window/command/phase/wall_ms/elapsed_ms/success`。每个请求依次记录 `start`（IPC 到达包装）、`body_complete`（业务读取完成并释放锁）、`return`（注入延迟结束，将返回响应）。据窗口筛选 `get_revision` 可计算校验请求数；据相同 id 的 body_complete/return 可证明延迟发生在取数之后。广播丢弃时另记 `event_dropped/event/revision`，证明开关真正消费。

这些日志不写数据库、不记录请求载荷，不新增产品命令；CommandProbe 所在模块及包装调用均带 debug 编译守卫。日志记录后端接收/返回时刻，不等于前端实际绘制时刻，仍须配合窗口观察。也不能用它单独证明隐藏期间 visibilityState；该状态需要从对应 WebView 控制台核对。临时替换 __TAURI_INTERNALS__.invoke 的脚本在本机未捕获真实调用，不作为时序证据。

## 1. 前置（**已落地**，`src-tauri/` 侧）

计划 Task 6a 指定的两个前置件**已经落地**。下面写的是它们的**实际形状**——第 2 节照这里
写；计划原文那几行写在契约冻结之前，不要照抄（差异见本节末尾）。

1. **第二个窗口 `sync-lab`**：`src-tauri/src/platform/sync_lab.rs` 用
   `WebviewWindowBuilder` 在实验时创建（**不是** `tauri.conf.json` 的静态窗口：启动时
   不会出现，`manual-shell.md` 的既有验收步骤不受影响）。窗口配置与主窗**同源**——
   读 `tauri.conf.json` 里 `main` 那一份、**只改 label**（入口 URL、标题、尺寸全一样），
   所以它跑的是同一份前端。
   `src-tauri/capabilities/default.json` 的 `windows` 已登记 `["main", "sync-lab"]`；
   「label 与配置/权限名单一致」由 `tests/shell_lifecycle.rs` 读那两个文件核对。
2. **四个 dev 注入命令**（`#[cfg(debug_assertions)]`，**只在 debug 构建编译**）：
   - `__p7_drop_next_event(kind)` —— 丢掉下一条**指定事件名**的通知（末次事件丢失）；
   - `__p7_delay_next_query_ms(command, ms)` —— 让**装开关那个窗口**里下一次指定命令的
     响应延迟返回（**先取数据再 sleep，绝不跨 `await` 持 `Connection`**）；
   - `__p7_replay_event(revision)` —— 用一条**旧 `revision`** 重播 `domain.changed`；
   - `__p7_open_sync_lab()` —— 开实验窗口（上面那条的触发入口）。

   落点：命令面在 `src-tauri/src/commands/dev.rs`；丢弃开关的状态在 `services/events.rs`
   的广播出口；延迟开关由命令包装（`commands/mod.rs` 的 `run_command`，键 = 调用方窗口
   label + 命令名）在**放锁之后**调。发布构建里它们**不存在**（命令体整份带守卫 +
   注册表里每条臂带守卫）；「发布构建的 handler 列表里没有它们」由
   `tests/dev_injections.rs` 读源码核对。

### 控制台怎么调（第 2 节各步的入口命令）

页面**没有** `window.__TAURI__`（`tauri.conf.json` 没开 `withGlobalTauri`），但 Tauri
注入的 `__TAURI_INTERNALS__` 一直都在。第 2 节里写作 `__p7_drop_next_event("domain.changed")`
的那几行，在 **DevTools 控制台**里就是：

```js
// ① 开第二个窗口（在 A/main 的控制台执行；返回值就是新窗口的 label）
await __TAURI_INTERNALS__.invoke("__p7_open_sync_lab")
// ② 丢掉下一条 domain.changed（在 B/sync-lab 的控制台执行）
await __TAURI_INTERNALS__.invoke("__p7_drop_next_event", { kind: "domain.changed" })
// ③ 让「这个窗口」下一次 list_tasks 的响应晚 10 秒返回（在 B 的控制台执行；§2.2 的 8–10 秒窗口）
await __TAURI_INTERNALS__.invoke("__p7_delay_next_query_ms", { command: "list_tasks", ms: 10000 })
// ④ 用旧 revision 重播一条通知（在 B 的控制台执行；R 见 2.3.2）
await __TAURI_INTERNALS__.invoke("__p7_replay_event", { revision: R - 1 })
```

**确认哪个窗口是哪个**：在任一窗口的控制台读
`window.__TAURI_INTERNALS__.metadata.currentWindow.label`（应为 `main` / `sync-lab`）。

⚠️ **三条开关的作用域不一样，别记混**：

- **丢弃**丢的是那一次**广播**本身（所有窗口都收不到）——所以 2.1 / 2.3.1 / 2.4 里 A 的
  界面照常更新（A 用的是**自己的命令响应**：捕获页成功之后当场重拉一次，不等通知）；
- **延迟**只作用于**装开关的那个窗口**：2.2 在 B 上装 ⇒ 被延迟的是 **B** 的那次重拉，
  不是先跑到的那次 A 的重拉（`sync-lab` / `main` 就是这里的键）；**窗口宽度按 §2.2 的
  8–10 秒给**，写太短会让操作追上窗口、判据失效；
- **重播**广播给所有窗口：两个窗口都会收到那条旧版本通知（判据仍然是 B 的展示不变）。

**两处与计划原文的差异（已按这里实现）**：

- 丢弃开关**按事件名筛**（计划原文不带筛选）：有活动会话时采样每秒广播一条 `timer.tick`，
  不筛的话「丢掉下一条」会被一条无害 tick 吃掉，实验看起来"什么都没发生"。
  实现是「事件名相同才消费掉开关」，`tests/dev_injections.rs` 有专门一条断言。
- 重播开关的参数是**旧 `revision`**（计划原文写 `event_seq`）：信封里没有 `event_seq`
  （00 §5 与 `src/types/ipc.ts` 的 `EventEnvelope` 是 `data_epoch` / `event` / `revision` /
  `at` / `payload`）。

**前置落地之前的限制已经解除**：第 2 节七步现在都能做。这几条规则的**规则侧**仍然由 6a 的
自动化用例钉住（对照表见 §4），实机补的是真实双 WebView 的广播时序。

## 2. 步骤

### 2.0 同时打开两个窗口

1. `pnpm tauri dev`（或安装包）启动，确认主窗 `main` 出现。
2. 在 **A（`main`）** 的 DevTools 控制台执行 §1 的第 ① 条
   `await __TAURI_INTERNALS__.invoke("__p7_open_sync_lab")`：Rust 侧按主窗那份配置建出
   第二个窗口，**返回值就是它的 label**（应为 `sync-lab`）；也可以在它的控制台读
   `window.__TAURI_INTERNALS__.metadata.currentWindow.label` 复核。它跑的是**同一份前端**
   （配置与主窗同源、只改 label）。
   - ⚠️ **同一窗口里的 DOM 分栏 / iframe / 普通浏览器标签页都不算第二个 JS 上下文**：
     本实验要的是**两个各自独立的 WebView**（各有自己的模块实例、自己的水位、自己的事件
     订阅）。同窗分栏共享同一个 `domainState`；浏览器标签页连 Tauri 后端都没有
     （`invoke` 直接失败）。拿它们做出来的"一致"不说明任何问题。
3. 两个窗口都切到「任务」页。
   - [ ] 两个窗口都有数据（不是加载态/错误态）；两边看到的列表**内容相同**
   - [ ] 两个窗口的 `document.visibilityState` 都是 `visible`（各自 DevTools 控制台）
   - 现象：
4. **怎么算不通过**：只有 `main` 一个窗口（`sync-lab` 没建出来）；第二个窗口的 label
   不是 `sync-lab`（`capabilities` 没登记 ⇒ 它的 JS 调命令全失败，现象是"一直在连接中/
   报错"）；或两边内容不一致（那本身就是 F-020 的展示不一致，先查这一条再往下做）。

### 2.1 竞态 (a)：末次事件丢失（`__p7_drop_next_event("domain.changed")`）

> 验的是 00 §5 规则 4：**末次通知丢了仍要能收敛**，靠可见窗口至多每 30 秒一次
> `get_revision` 校验（隐藏窗口在显示前校验）。

1. **前置**：B（`sync-lab`）能看到任务列表；记下 B 列表里有几条、最后一条是什么。
2. **注入**：在 B 的 DevTools 控制台执行 `__p7_drop_next_event("domain.changed")`。
3. **触发**：切到 A（`main`），在收件箱里捕获一条新任务，例如标题 `实机-a-<时刻>`。
   - [ ] A 的列表里立刻出现这条任务（A 自己的命令响应）
   - [ ] **B 的列表里还没有它**（那条通知被丢了）→ 现象：
4. **等**：看秒表，从 A 提交那一刻起，**不碰 B**（不要切页、不要点刷新）。
   - [ ] B 在**≤ 30 秒内启动校验**；随后列表自己出现这条任务。分别记录校验启动耗时：____ 秒，查询/渲染耗时：____ 秒，总展示耗时：____ 秒。
     （校验启动须由开发计数/日志直接证明；debug 包装日志可证明真实 get_revision 到达时刻；前端调度/绘制诊断仍归 P8，不能用“31 秒内出现”代替调度证据，也不能把 IPC/渲染耗时算作轮询间隔。）
   - [ ] 这期间 `SELECT revision FROM app_meta WHERE singleton = 1` 一直是 A 写完之后那个值
     （不是"又多涨了几次"）
   - 现象：
5. **怎么算不通过**：可见窗口超过 30 秒尚未启动校验，或校验成功后列表仍缺任务；60 秒只作为挂起诊断阈值，不能用它放宽通过标准。或 B 出现了任务但 `revision` 又变了
   （说明不是校验收敛，而是别的写入）。

### 2.2 竞态 (b)：旧响应晚到（`__p7_delay_next_query_ms("list_tasks", 10000)`）

> 验的是 00 §5 规则 3 的后半句：**查询响应比已应用/所需版本旧时不得覆盖**。
>
> ⚠️ **必须在「同一个问题」上造**（fix round 1，评审指出旧写法不可证伪）：如果被延迟的那条
> 查询问的是**另一个问题**（例如"先切到等待中再切回来"），那么它回来时有**两条**判据会丢它
> ——① 问题身份（它回答的不是现在这个问题）② 版本（比已上屏的那份旧）。判据②单独坏掉时
> 现象一模一样，这一步就会**假阴性**。所以下面用「**同一问题、两条响应**」：A 连写两次
> ⇒ B 在**同一个筛选**下重拉两次，第一条响应被延迟，第二条先到并上屏。
>
> ⚠️ **延迟窗口必须比操作快**（fix round 1 复评，第二条订正）：窗口是 **8–10 秒**，
> 不是 5 秒。操作一旦慢于窗口，被延迟的那份响应会**先回来并被正常接纳**（它并不旧），
> 于是这一步**悄悄失去判别力、却仍然会记「通过」**。下面第 3 步的第一条勾选就是用来
> 当场确认「注入此刻还有效」的。

1. **前置**：两个窗口都在「任务」页，**筛选条件保持一致、全程不改**；记下两边列表的最后一条。
2. **注入**：在 **B** 的控制台执行 `__p7_delay_next_query_ms("list_tasks", 10000)`
   （**8–10 秒**；写 5000 会让操作时间逼近窗口宽度，见上面的第二条 ⚠️）。
3. **触发 A 连写两条**：切到 A，在延迟窗口内（8–10 秒）**连续**捕获两条任务：
   `实机-b-1-<时刻>`、`实机-b-2-<时刻>`（每条一次提交）。
   - [ ] **在写第二条之前，B 的列表里还没有 `实机-b-1-…`**
     （**前置勾选，必查**：此刻被延迟的那份响应还没回来。若它已经回来了，说明这一趟
     操作慢于窗口 ⇒ 本条判据已经失效，**作废重做**，不要记「通过」）
   - [ ] B 收到第一条 `domain.changed` 后的那次重拉**被延迟**（页面短暂停在旧列表/加载态）
   - [ ] B 收到第二条 `domain.changed` 后的那次重拉**没被延迟**：列表里出现 `实机-b-2-…`
     （以及 `实机-b-1-…`）
   - [ ] 延迟窗口过后（约 10 秒）那条被延迟的响应（**只含 `实机-b-1` 的那一版**）回来：
     **B 的列表里 `实机-b-2-…` 仍然在**——旧版本的那份被丢弃，没有覆盖已经上屏的新状态
   - [ ] 全程 B 的筛选条件没变过（问题身份不变 ⇒ 能挡住那份旧响应的**只有版本判据**）
   - 现象（含 B 列表内容的变化时刻）：
4. **怎么算不通过**：延迟的那份响应回来之后 B 的列表**少了 `实机-b-2-…`**（或整屏换成
   只含 `实机-b-1` 的旧内容）——那就是"旧响应覆盖了新状态"。
   若那份响应干脆没回来（注入开关没生效），记「注入未生效」，**不要记「通过」**。
   **第 3 步第一条勾选没打上，同样不要记「通过」**——那说明这一趟根本没造出竞态。

### 2.3 竞态 (c)：乱序 / 跳号通知

> 验的是 00 §5 规则 5 与规则 3：**跳号/乱序无法证明一致时取新快照**；同 epoch 且
> `revision <=` 已应用/已见版本的通知被丢弃。

#### 2.3.1 跳号 ⇒ 取新快照并收敛

1. **注入**：在 **B** 的控制台执行 `__p7_drop_next_event("domain.changed")`
   （把 A 的**第一条**写通知丢掉）。
2. **触发**：在 A 上**连续**捕获两条任务（每条一次提交）：`实机-c1-1`、`实机-c1-2`。
   - [ ] B 只收到了第二条那条通知（`revision` 比它已见的多了不止 1 ⇒ 跳号）
   - [ ] **B 的列表里两条都在**（跳号后取了一份新快照，而不是"就地补课"只加一条）
   - [ ] B 的列表与 A 的列表**内容一致**（同一条任务不重不漏）
   - 现象：
3. **怎么算不通过**：B 的列表只出现第二条（缺 `实机-c1-1`），或出现重复条目。

#### 2.3.2 旧 `revision` 重播 ⇒ 丢弃，展示不变

1. **前置**：先记下 B 列表当前内容与 `SELECT revision FROM app_meta WHERE singleton = 1`（记作 R）。
2. **注入**：在 **B** 的控制台执行 `__p7_replay_event(R - 1)`（重播一条**旧版本**的通知）。
   - [ ] B 的列表**完全没有变化**（不闪、不重排、不少条目）
   - [ ] B 没有因此多取一次快照/重拉（若注入开关带计数，记下计数不变；否则看网络/日志）
   - 现象：
3. **怎么算不通过**：B 的列表因为一条更旧的通知而刷新出旧内容。

### 2.4 时序验证：A 暂停 ⇒ B 的展示在 30 秒内收敛

> 6b 的「时序验证」第一条。⚠️ 与 `manual-shell.md` §2A/2B 的**前置状态**不同：
> 那两节验的是"关掉全部窗口后核心还在跑"，这一节验的是**跨窗口的展示收敛**。

1. **前置**：在 A 上开始一次计时（会话 `running`），两个窗口都切到「计时」页；
   两边都显示在跑，记下 A 上那条会话的 `session_id`
   （`SELECT id FROM work_session WHERE run_id = '<上面取到的 run id>'`）。
2. **注入**：在 **B** 的控制台执行 `__p7_drop_next_event("domain.changed")`
   （把"A 暂停"那条业务通知丢掉）。
3. **触发**：在 A 上点「暂停」。
   - [ ] A 的计时区立刻变成已暂停（命令响应）
   - [ ] **B 的计时区还在跑**（那条通知丢了）→ 现象：
4. **等**（同一块秒表，从 A 点下暂停那一刻起）：
   - [ ] B 的计时区在 **≤ 30 秒**内变成已暂停，暂停值不再增长；记下**实测秒数**：____ 秒
   - [ ] `SELECT state FROM work_session WHERE run_id = '<上面取到的 run id>'` = `paused`
   - 现象：
5. **怎么算不通过**：B 超过 30 秒仍是 running；或 B 变成 paused 但暂停值还在增长
   （那是展示值没有按快照落定）。

### 2.5 时序验证：B 隐藏后重新显示，先校验再展示

1. **前置**：两个窗口都切到「计时」页，A 上正在计时。
2. **最小化 B**，在 B 的控制台确认 `document.visibilityState === "hidden"`；仅被其它窗口遮挡不保证 hidden，若仍 visible，本次不能作为隐藏窗口验收。
   - [ ] 在 debug CommandProbe 日志中，确认该窗口隐藏后的完整35秒观察段内，没有新的 `get_revision` start。进入隐藏前已发出的响应不计为新轮询；其它窗口的请求单独计数。
   - 现象：记录 hidden 确认时刻、观察结束时刻与窗口 label；如果无法确认 hidden，记「前提未满足」，不要记通过。
   - **Windows / WebView2 注意**：原生 `isMinimized()` 为 true 不代表 `document.visibilityState` 为 hidden。2026-10-05 实机观察到原生最小化但页面仍 visible、周期校验仍继续；该场景须单独登记，不可把它当 hidden 场景通过。后续原生窗口可见性适配需同时复验最小化和恢复，不要修改浏览器属性来伪造实机结果。
3. **在 A 上暂停**（不要丢通知：这一节验的是"显示前校验"，不是"通知丢了也能收敛"）。
4. **恢复 B**：
   - [ ] B 一显示出来就是**正确的暂停态**（第一眼就对；不是先显示 running、等下一拍通知才纠正）
   - [ ] 从该窗口 debug CommandProbe 的 `get_revision` start 记录确认恢复触发校验；记录恢复时刻、请求入口时刻和首次界面观察时刻。后端日志证明请求到达，不能单独证明绘制前后顺序；没有首屏录像时，对瞬时旧态闪烁保留未验证。
5. **怎么算不通过**：B 恢复后第一眼是 running，过一会儿才变 paused。
